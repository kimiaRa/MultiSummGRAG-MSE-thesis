# E5 — Human validation sampling

No model calls, no network calls. Set A drawn from `evaluation/results/e1_claims.csv` (Part 1's own output); Set B drawn via `e1_evidence_consistency.parse_ledger_pdf` (Part 1's reused ledger extractor). Fixed seed 42 throughout -- both the stratum allocation's remainder tie-breaks and the within-stratum sampling draws. Generated by `evaluation/e5_sample_for_annotation.py`.

## Set A — 50 claims, stratified system x city x label

Allocation uses a capacity-aware equal split (`allocate_equal`, a water-filling scheme): every non-empty (system, city, label) stratum gets as close to an equal share of 50 as its own size allows; any shortfall from strata too small to take their equal share (several are -- pipeline UNSUPPORTED is 0 rows for 4 of 5 cities) flows to the remaining strata in further rounds, rather than shrinking the sample below 50 or leaving it unevenly weighted toward the largest strata. This is a deliberate choice for *coverage* (every combination that has any data gets checked) over strict population-proportional sampling, which would have handed nearly the whole sample to the largest strata (pipeline SUPPORTED) and left several conditions unchecked.

## Set B — 40 ledger rows, 8 per city, stratified across decision

Per city: `allocate_equal({Retained: n, Discarded: n}, 8, rng)` -- as close to 4/4 as that city's ledger allows (all 5 cities have far more than 4 of each, so every city gets an exact 4/4 split). Rows with `decision=UNKNOWN` or no extractable Candidate-column URL are excluded from the sampling frame before allocation -- ledger-extraction failures (2 rows in Barcelona, 1 in London, 0 elsewhere), not a genuine decision category.

## Set C — 25 claims, all AUDITABLE_DIRECT

Added after this file's initial generation (`evaluation/scripts/enrich_set_c.py`), so it is not covered by the sampling design above: all 25 items are pipeline claims E1 labelled AUDITABLE_DIRECT, each enriched with every evidence-base key path (`candidate_slots`) that holds the exact claimed value. There is no separate withheld ground-truth file for Set C -- the human judgement (CORRECT_SLOT / WRONG_SLOT / UNCLEAR) against the enriched candidate list *is* the verdict, since the question is whether the value is applied to the quantity it actually measures, which only a human reading the sentence can decide.

## Scoring

Annotation and scoring are complete. `evaluation/scripts/score_annotation.py` (generic pooled scorer, written before Set C existed) was **not** used for the final numbers: pooling Set A would misrepresent it, since its 20-item sample was deliberately weighted 6/10/4 toward the error-prone classes rather than proportional to their true population split (see the allocation table above) -- a pooled figure would not estimate population-level agreement. Instead, `evaluation/scripts/e5_final_stats.py` scores all three sets with the appropriate per-stratum/exclusion handling for each and writes `evaluation/results/e5_final_stats.csv` and `evaluation/results/e5_final_stats.md` (full tables, every disagreement listed in full).

**Headline results:**

- **Set A** (per-stratum, no pooled figure): AUDITABLE_DIRECT 0/4 agree, AUDITABLE_DERIVED 5/10, NOT_MACHINE_AUDITABLE 3/6. Weak agreement in every stratum; full detail in `evaluation/results/e5_final_stats.md`'s Set A section. **Set A is not part of the final thesis evaluation** (superseded; not cited by `evaluation/E1_SUMMARY_v2.md`).
- **Set B**: 5 of 40 rows excluded (3 UNREACHABLE_NOW, 2 UNCLEAR); of the remaining 35, raw agreement 68.6% (24/35), Cohen's kappa 0.368; directionality 7 mine-retained-ledger-discarded vs. 4 the reverse. Full detail in `evaluation/results/e5_final_stats.md`'s Set B section. **This scores the retired, pre-baseline_v2 ledger only** (`evaluation/e5_sample_for_annotation.py` drew Set B from `e1_evidence_consistency.parse_ledger_pdf`, the retired PDF ledger extractor) -- it is not evidence about baseline_v2. For baseline_v2's own human screening reproducibility check, see `evaluation/results/baseline_v2_human_screening_validation_summary.md`.
- **Set C**: 0 WRONG_SLOT of 25 (95% exact binomial CI 0.0%-13.7%); no misattribution found in this sample. **This is final thesis evidence.** Full detail in `evaluation/results/e5_final_stats.md`'s Set C section.

**Two data-provenance issues surfaced during scoring, both resolved and documented in `e5_final_stats.py`'s docstring and printed output:**

1. The files this design doc's own annotation flow points to as "annotated" (`e5_set_a_reduced.csv`, a 20-item reduction of Set A used for the weighted sample; `e5_set_c_enriched.csv`) had MY_LABEL blank for every row at scoring time -- `e5_set_c_enriched.csv` because `enrich_set_c.py` was re-run after annotation and regenerated it from the unannotated source, clobbering the labels. The real annotations, identical in every other column, were saved under sibling filenames (`e5_set_a_annotated.csv`, `e5_set_c_annotated.csv`) and used instead. `e5_set_c_annotated.csv` no longer exists under that name; a 2026-08-27 read-only audit confirmed the same annotated data (25/25 CORRECT_SLOT, unchanged) now lives directly in `e5_set_c.csv`, which is the canonical Set C source `e5_final_stats.py` reads.
2. Set A's withheld `label` column uses an older token set (SUPPORTED/DERIVED/UNSUPPORTED, matching the wording in this file's own allocation table above) than the AUDITABLE_DIRECT/AUDITABLE_DERIVED/NOT_MACHINE_AUDITABLE taxonomy `e1_claims.csv` uses today -- `e1_claims.csv` was evidently relabelled after this file's Set A sample was drawn. Confirmed a straight rename, not a reclassification, by exact per-class count match (411/52/172) against the current label column.

Re-running `evaluation/e5_sample_for_annotation.py` regenerates this file from scratch (design section only, not this Results section) and would draw a new seed-42 sample against whatever `e1_claims.csv` looks like at that time -- not necessarily the same 50/40 items scored above.
